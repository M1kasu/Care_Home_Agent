# 兴享智家·慧家中枢需求文档

## 1. 项目概述

“兴享智家·慧家中枢”是一套面向家庭场景的端侧智能体系统。系统运行在家庭网关、轻量化边缘盒子、开发板或普通低功耗主机上，通过本地轻量模型、规则化任务规划、本地知识库和工具函数调用，实现家庭网络诊断、智能家居控制、老人关怀提醒、家庭知识问答和多轮对话协同。

本项目强调在不超过 6 TOPS 算力、4GB 内存的典型端侧设备约束下完成可用智能服务。系统优先在本地处理家庭成员信息、设备状态、健康提醒和网络日志，避免把敏感家庭数据上传到云端。

## 2. 建设目标

1. 构建一个可运行的端侧家庭智能体 Demo，满足自然语言交互、任务规划、工具调用和状态保持能力。
2. 通过模拟家庭设备、网络节点和家庭成员档案，展示智能体对真实家庭场景的理解与执行能力。
3. 在有限算力下实现低延迟响应，提供可量化的资源占用和性能展示。
4. 形成可提交比赛的方案文档、代码说明、接口文档、测试脚本和演示视频素材。

## 3. 目标用户

1. 普通家庭成员：通过自然语言控制家庭设备、查询家庭状态、处理日常提醒。
2. 老年家庭成员：获得吃药、饮水、休息、异常情况提醒等关怀服务。
3. 家庭管理员：查看设备状态、网络质量、能耗信息和家庭提醒任务。
4. 运营商或家庭终端厂商：将端侧智能体能力集成到家庭网关、智能屏、路由器、机器人等产品中。

## 4. 场景痛点

### 4.1 设备割裂

家庭中可能同时存在路由器、智能灯、空调、摄像头、门锁、音箱、健康设备等终端。不同设备来自不同品牌，用户需要在多个 App 之间切换，操作成本高。

### 4.2 家庭网络问题难定位

家庭 Wi-Fi 卡顿、视频会议掉线、老人房间信号弱等问题很常见，但普通用户难以理解信道干扰、设备占用、Mesh 节点状态、带宽分配等技术信息。

### 4.3 老人关怀缺少上下文

普通提醒工具只能定时响铃，无法结合家庭状态、设备状态和多轮对话进行柔性提醒。例如用户说“爷爷准备睡了”，系统应能联动提醒吃药、调暗灯光、关闭客厅电视并检查门锁。

### 4.4 云端方案存在隐私顾虑

家庭成员作息、健康提醒、室内设备、摄像头状态和网络日志都属于敏感信息。完全依赖云端大模型会增加隐私传输风险，也会受网络稳定性影响。

## 5. 核心价值

1. 本地智能：家庭敏感数据优先在端侧处理，提升隐私安全。
2. 统一入口：用自然语言统一调度网络、设备、提醒、知识库等能力。
3. 低成本部署：采用轻量模型和规则规划器，适合家庭网关或轻量边缘设备。
4. 可解释执行：每次任务拆解、工具调用和执行结果均可展示，便于演示和排错。
5. 可产品化扩展：可接入真实路由器、智能家居协议、健康设备和运营商家庭服务。

## 6. 功能需求

### 6.1 自然语言理解

系统应支持用户用自然语言描述家庭任务，并识别意图、槽位和上下文信息。

示例：

- “帮我把家里切到睡前模式。”
- “爷爷今晚吃药了吗？”
- “卧室视频有点卡，帮我看看原因。”
- “如果客厅没人了，就把电视和灯都关掉。”

系统需要识别的基础意图包括：

1. 场景模式切换：睡前模式、离家模式、回家模式、观影模式、学习模式。
2. 设备控制：开关、亮度、温度、模式、区域、目标设备。
3. 网络诊断：卡顿、掉线、信号弱、设备占用、信道干扰。
4. 关怀提醒：吃药、饮水、休息、复查、异常未响应。
5. 知识问答：家庭规则、老人用药注意事项、设备使用说明。
6. 任务追问：当槽位缺失时主动询问用户补充信息。

### 6.2 任务规划

系统应将用户指令拆解为可执行任务步骤，并按照依赖关系顺序执行。

示例任务：

用户输入：“爸妈准备睡了，帮我切到睡前模式，顺便看看卧室网络为什么卡。”

规划结果：

1. 查询卧室、客厅、门锁、空调、路由器状态。
2. 将客厅灯光调暗并关闭电视。
3. 将卧室空调调整到睡眠模式。
4. 检查门锁是否关闭。
5. 检查老人吃药提醒是否完成。
6. 执行卧室 Wi-Fi 诊断。
7. 汇总执行结果并给出建议。

### 6.3 工具调用

系统应通过本地工具函数完成实际动作或模拟动作。工具函数包括：

1. 设备控制工具：控制灯、空调、电视、门锁、插座等。
2. 网络诊断工具：查询带宽占用、信号强度、延迟、信道干扰和 Mesh 节点状态。
3. 提醒管理工具：创建、查询、完成、取消提醒。
4. 家庭档案工具：查询家庭成员、房间、设备归属关系。
5. 本地知识库工具：检索家庭规则、设备说明和健康注意事项。
6. 安全确认工具：对门锁、摄像头、异常告警等敏感动作进行确认。

### 6.4 多轮对话与状态保持

系统应保持对话上下文，支持用户基于上一轮继续发出指令。

示例：

用户：“卧室网络有点卡。”

系统：“检测到卧室 Mesh 信号偏弱，电视正在占用较高带宽。是否要优先保证卧室视频通话？”

用户：“先保证爷爷那边。”

系统应理解“爷爷那边”指老人卧室，并执行对应 QoS 策略。

### 6.5 本地知识库

系统应支持在本地保存和检索家庭相关知识，包括：

1. 家庭成员档案。
2. 房间与设备清单。
3. 药品和健康提醒说明。
4. 家庭网络拓扑。
5. 常见问题处理流程。
6. 用户自定义家庭规则。

### 6.6 性能展示

系统应展示或记录以下指标：

1. 单轮响应耗时。
2. 模型推理耗时。
3. 工具调用耗时。
4. 内存占用估计。
5. 任务成功率。
6. 本地数据命中率。

### 6.7 演示界面

Demo 应包含一个简洁可视化界面：

1. 对话输入与回复区域。
2. 设备状态面板。
3. 家庭网络状态面板。
4. 工具调用日志面板。
5. 任务规划步骤面板。
6. 性能指标面板。

## 7. 非功能需求

### 7.1 端侧资源约束

系统设计应满足典型端侧设备可承载要求：

1. 算力：不超过 6 TOPS。
2. 内存：目标运行内存不超过 4GB。
3. 部署：支持 Python 本地运行，可迁移到嵌入式 Linux 环境。
4. 模型：支持轻量模型或模拟轻量推理模块。

### 7.2 隐私与安全

1. 家庭成员档案、健康提醒、设备状态和网络日志默认本地保存。
2. 不依赖云端上传敏感数据完成核心流程。
3. 门锁、摄像头、告警通知等敏感动作需要二次确认或安全策略限制。
4. 日志中避免保存明文敏感信息。

### 7.3 可扩展性

1. 工具函数采用统一注册机制，方便新增设备或服务。
2. 意图识别与任务规划解耦，方便替换模型。
3. 知识库模块可从简单关键词检索升级为向量检索。
4. 设备模拟层可替换为真实 IoT 协议适配层。

### 7.4 可维护性

1. 代码结构清晰，包含入口函数 main.run。
2. 提供 README、接口文档和测试脚本。
3. 样例数据与业务逻辑分离。
4. 关键工具调用有日志记录。

## 8. 约束与假设

1. 初赛阶段可以使用模拟家庭设备和模拟网络数据完成演示。
2. 初赛阶段优先保证 Demo 完整度，不强制接入真实硬件。
3. 系统可以使用公开预训练轻量模型，也可以提供可切换的规则推理后备模式。
4. 比赛不提供语料，项目自行构造家庭场景数据、设备数据和多轮对话测试集。

## 9. 验收标准

1. 用户输入自然语言指令后，系统能输出任务规划步骤。
2. 系统能调用至少 5 类工具函数并返回结构化结果。
3. 系统能完成至少 3 个典型家庭场景演示。
4. 系统能在多轮对话中保持上下文。
5. 系统能展示本地知识库检索结果。
6. 系统能展示响应耗时和工具调用日志。
7. 项目包含 main.py，且提供 run 入口函数。
8. 项目包含简易部署和测试说明。

## 10. 典型演示用例

### 10.1 睡前模式

用户：“爸妈准备睡了，帮我切到睡前模式。”

预期效果：

1. 关闭客厅电视。
2. 调暗客厅灯光。
3. 将卧室空调设置为睡眠模式。
4. 检查门锁状态。
5. 检查老人吃药提醒。
6. 输出执行总结。

### 10.2 卧室网络诊断

用户：“卧室视频有点卡，帮我看看。”

预期效果：

1. 查询卧室信号强度。
2. 查询高带宽设备。
3. 检查 Mesh 节点状态。
4. 给出优化建议。
5. 支持用户继续说“先保证爷爷那边”，并调整优先级。

### 10.3 老人关怀提醒

用户：“提醒爷爷晚上九点吃降压药，没回应的话再提醒一次。”

预期效果：

1. 创建吃药提醒。
2. 绑定家庭成员和药品信息。
3. 设置未确认后的二次提醒策略。
4. 支持查询“爷爷今天的提醒完成了吗”。

### 10.4 家庭知识问答

用户：“爷爷睡前能不能喝浓茶？”

预期效果：

1. 检索本地健康注意事项。
2. 给出简洁建议。
3. 提醒该建议不是医疗诊断。
